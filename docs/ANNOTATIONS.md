# File annotations (luxfs xattrs), light usage

Status: first convention, 2026-10-28. Tools: `~/src/luxfs` (`x` writes, `lsx` reads; see its README).
Everything here is optional and best effort: a file without attributes is fine, a filesystem without
user xattrs is fine, nothing depends on them.

## Attributes we use
| `x` name | on disk | meaning | example |
| --- | --- | --- | --- |
| `desc` | `user.lux.desc` | one line: what this file is | `Jade 4074 visual style` |
| `author` | `user.lux.author` | who made the content: `microsoft`, `wine`, `aap`, `claude`, `gpt`, or a tool name for generated files (`lhde-import`) | `microsoft` |
| `source` | `user.lux.source` | where it came from, or "generated by X from Y" | `Longhorn 4074 (6.0.4074.0), WINDOWS/system32/imageres.dll` / `generated by lhde-import recipe imageres from 4074/system32/imageres.dll` |
| `build` | `user.lux.build` | the Windows build a file belongs to | `4074`, `5112`, `xp`, `2k` |
| `tags` | `user.xdg.tags` | free tags, comma separated (stored without spaces: `x` and flxp write `a,b`) | `aerovision,reference` |
| `comment` | `user.xdg.comment` | free text, as many lines as it needs (freedesktop's name): the elaborate field beside the one-line `desc` | |
| `color` | `user.lux.color` | a colour label: a name of the palette below, lower case | `red` |
| `run` | `user.lux.run` | the command the file opens with instead of its type's program: a `/bin/sh` command line, `%f` the file | `python3 %f`, `wine %f` |
| `notes`, `todo` | `user.lux.notes`, `.todo` | free text, as luxfs defines them | |

On FreeBSD the same attributes are extattr(2)'s, in the user namespace without the `user.` prefix (`getextattr user lux.desc
FILE`, `setextattr user xdg.tags a,b FILE`); lhde's programs and tools take the names above on both systems.

The colours (flxp's palette, `shell::details::palette`): `red`, `orange`, `yellow`, `green`, `teal`, `blue`, `purple`, `pink`,
`brown`, `gray`; VGA's values where VGA has the colour, a choice that reads on white and on the task band's blue. A value
outside it is kept and shown as written. Where a colour shows is a first, provisional choice (todo_ideas/xattribs.txt).

Tags in use (extend freely): `reference` (real Windows screenshots and originals to compare against),
`concept-art`, `research` (notes and findings), `generated` (rebuildable output), `aerovision`,
`slatevision`, `classic`, `navbar`, `frames`, `taskbar`, `sidebar`, `wallpaper`, `font`.

## The shared names
`desc`, `tags`, `comment`, `color` and `run` are general: flxp shows and edits them as the Explorer's Description, Tags,
Comment, Color and Run as (Details columns, the infotip, XP's Details rollout, 4051's task band, the context menu's Add Tag...
and the Properties sheet; docs/USAGE.md "Metadata"); its property registry (`flxp/shell/details.cpp`) maps each property to
its attribute. The description is one line and the comment the free text of several: flxp writes a description with its line
breaks as spaces, a comment with its lines (LF, not an edit control's CR LF); where a row has one line (a column, the band, the
infotip) a comment shows its first line and "…" when more follow. One free-text field is enough for the Explorer: luxfs's
`notes` and `todo` stay plain names, listed and edited in the Properties sheet's Advanced view only. flxp writes as `x` does:
values trimmed, without a trailing newline; tags split at commas (flxp also takes semicolons), trimmed, without duplicates, in
their order; a colour of the palette as its lower-case name; an emptied value removes the attribute. It reads a value whatever
its length (its size first), and takes only "not set" (`ENODATA`) or "no user attributes here" (`ENOTSUP`) as no value: on any
other read error a change (a new tag merged in, an edited description) is refused, not written over the unseen value. `author`,
`build`, `source`, `notes` and `todo` are this research's own and flxp's views do not show them.

`run` is the user's own setting, as a Windows shortcut's target is: a double click (or Open, or Enter) on a file that has it
runs the command with `%f` replaced by the file's path (quoted for the shell; `%%` a percent sign; without `%f` the path is
appended), in the file's folder, and asks nothing; Open With still offers the type's programs. A file keeps it where its
attributes travel (below): a copy made without them, a download or an archive unpacked without `--xattrs`, has none.

The Properties sheet (`shell::properties` in `flxp/shell/ui`, docs/USAGE.md "Metadata": the Explorer's Properties,
and `luxattr` from a terminal) is the GUI for all of them: its Metadata page edits `desc` (one line), `tags` (a list of the
files' tags with a box to add from the known ones), `color` (a row of swatches), `comment` (several lines) and `run` (with a
Browse... for the program), and its Advanced view lists, edits, adds and removes any `user.*` attribute (`author`, `source`,
`build`, `notes`, `todo` among them), on one file or several at once. It writes through the same code as flxp
(`shell::details::write` and `change_tags`; any name the registry does not know as a text, trimmed, its lines kept), lists the
names with `shell::details::list_attrs`, and luxattr needs no session.

## Where they are set
- `lhde-import` annotates what it writes into the Windows tree: originals get `author = microsoft`,
  `build`, `source` (image and in-image path), `desc`; generated files get `author = lhde-import`,
  `source = generated by recipe R from F`, `tags = generated`. `--no-annotate` turns it off. A style dropped in by hand gets
  `desc` (its name); a known Aero patch (lhdetree.py `AERO_PATCHES`, by sha256: RealAero's releases, TWIWMTB's Aero; docs/USAGE.md
  "The Aero patches for 4074") gets its `author` (`Lucas Brooks`, `BOFH`), `build = 4074`, what it is in `desc` and where it was
  published in `source`; an unknown one (the private Aero's DemoCheck with 4074's CompositedWindow parts) gets `author = unknown`
  and `desc` saying so. `lhde-theme explain` shows the `desc` (it shows a style's `desc` when its `author` is set and not
  `microsoft`).
- `lhde-pack` writes the same attributes on the pack's files and directories (`source` is then the medium's real in-image
  path, as in the MANIFEST) and makes the tarball with `tar --xattrs --xattrs-include='user.*'`; `lhde-import --pack` extracts
  with `--xattrs` and copies them into the Windows tree. `--no-annotate` on either tool turns it off.
- `lhde-import --annotate` annotates an existing tree (one imported before this convention): it only adds
  attributes that are missing, so it is idempotent and keeps what you wrote; `source` of an original is then reconstructed
  from the source's `[files]` rules (a setup file's compressed name, e.g. `SHELL32.DL_`, is not recoverable that way).
- Best effort: a filesystem without user xattrs gives one warning, and the import goes on.
- The research workspace `~/fun/longhorn` (screenshots, references, notes, comparison images,
  extracted resources' top directories) is annotated by hand or by agents.

## Limits
- git does not store xattrs: files in this repository carry their history in git, not in attributes.
- Copies keep attributes only with `cp -a` (or `--preserve=xattr`), `rsync -X`, `tar --xattrs`.
- Reading: `lsx DIR` (descriptions), `lsx -t DIR` (tags), `lsx FILE` (everything), `lsx -x source DIR`.
